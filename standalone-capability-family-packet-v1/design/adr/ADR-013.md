# ADR-013: Plectarium relationship, family namespace, and portfolio ownership

**Status:** Accepted  
**Date:** 2026-08-31  
**Decisions:** `FAM-035`, `FAM-036`

## Context

The initial capabilities now participate in a suite named Plectarium and will
be published in repositories named for their canonical characters. The
existing provisional discovery and result-reference contracts identify only a
capability, which is ambiguous when Plectarium supports more than one family.
The portfolio also needs one owner for each mutable class of product truth so
suite, family, capability, workspace, and harness concerns do not drift into a
monorepo or competing canonical copies.

The canonical character specification and `FAM-034` already establish the ten
character identities. This ADR preserves them unchanged.

## Decision

1. **Plectarium** is the suite brand and is part of the Octon ecosystem. The
   relationship creates neither an Octon-prefixed formal name, runtime
   dependency, nor authority transfer. Plectarium is not an eleventh
   capability.
2. The family repository owns family constitution, invariants, character
   registry, shared provisional contracts, seeds, relationship graphs, and
   family change control. Plectarium, individual capability, workspace, and
   harness repositories retain the separate ownership boundaries in
   `spec/portfolio-source-ownership.md`.
3. The canonical machine family identifier is exactly
   `standalone-capability-family`. Provisional manifest, result-envelope, and
   result-reference identities carry `family_id` alongside descriptive
   `capability_id` and capability version.
4. Exact capability repositories use the canonical lowercase character names:
   `verity`, `titra`, `ortha`, `genea`, `echo`, `harmia`, `iris`, `janus`,
   `atlas`, and `sibyl`, mapped in
   `spec/family-identity-and-repository-map.md`.
5. Downstream capability packets and Plectarium pin a published family commit,
   packet version, packet-manifest digest, and used seed paths. They consume
   rather than fork family-owned contracts.
6. A shared SDK/runtime remains deferred until Verity, Titra, and Ortha supply
   implementation evidence and a later accepted family ADR authorizes
   extraction.

## Consequences

- Packet version 1.2.0 introduces a breaking but still provisional namespace
  migration for v0 manifest/envelope/reference documents.
- Consumers must validate the full family/capability/version identity tuple.
- Repository names no longer remain proposed, but CLI, package, image, schema,
  skill, and protocol names remain separate decisions.
- The family packet does not become a Plectarium implementation or suite bill
  of materials.
- No namespace, character, repository, suite, or ecosystem relationship grants
  permission, trust, compatibility, or downstream authority.

## Alternatives considered

- Hard-code the initial ten capabilities into Plectarium without a family
  namespace. Rejected because it prevents coherent future multi-family
  discovery and creates identifier collision risk.
- Let Plectarium own or fork the family contracts. Rejected because it creates
  two mutable canonical sources and reverses the family-to-suite dependency.
- Prefix every formal product and repository with Octon. Rejected because the
  accepted suite brand is Plectarium and the ecosystem relationship is not
  product identity or runtime coupling.
- Extract a shared runtime while creating the repositories. Deferred because
  the required three-capability implementation evidence does not yet exist.

## Migration and compatibility

`spec/migrations/provisional-family-namespace-1.2.0.md` defines the exact v0
document changes. Because all affected schemas remain `PROVISIONAL`, the
packet updates them in place while requiring explicit rejection of legacy
unnamespaced documents. No engine or published stable protocol is represented
as migrated by this foundation task.

## Reconsideration

Changing the family identifier, source-owner boundaries, or exact repository
mapping requires a successor family decision and compatibility/migration
analysis. Shared runtime extraction additionally requires the existing
three-capability evidence threshold.
