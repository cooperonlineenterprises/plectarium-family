# Universal Code Audit — Full Product Build Packet Generation Directive

Act as the principal product architect, domain specialist, systems architect, security architect, evidence-systems architect, developer-tooling architect, Agent Skill architect, verification architect, AI-team operating-model designer, specification editor, and technical program lead for **Universal Code Audit**.

Your job is not to implement the product yet. Generate a canonical, production-grade **Product Constitution + Executable Specification + AI Build Packet** for a new independent repository.

## Established character identity

The canonical character identity is **Verity**. Preserve Verity consistently in user-facing documentation, Agent Skills, help, UI, harness projections, and reports. Do not introduce nicknames or competing character names. Preserve the descriptive capability ID and the exact repository identity established by the family map; treat CLI, package, image, schema, skill, and protocol identifiers as separate decisions. Anthropomorphic language never grants project, execution, or downstream authority.

## Product definition

**Governing question:**

> **What appears risky, defective, inconsistent, costly, structurally unhealthy, unnecessarily complicated, or safely removable in this codebase?**

**Purpose:** Produce reproducible repository intelligence and code-audit evidence by combining structural, historical, graph, test, dependency, runtime-imported, security, and optional semantic evidence.

**Mature target:** A production-grade, language-aware, local-first audit engine with CLI, CI, MCP, OCI, durable evidence, stable comparison, deep Rust/Python support, useful TypeScript/JavaScript and Go support, selected mature adapters, and two evaluated Agent Skills.

The product owns:

- repository identity and scope
- repository discovery
- history and graph intelligence
- audit planning
- candidate validation and attempted refutation
- stable findings
- Reduction/Simplification lens
- audit comparison
- UCA Audit Bundle

The product does not own:

- project authority
- automatic remediation
- source-control actions
- release or deployment authority
- specialist analyzer reimplementation
- Octon Mini governance

The capability produces evidence and bounded conclusions. It never acquires downstream project authority merely because its result is high confidence.

Do not mechanically copy UCA’s candidate/finding model. Define the domain model appropriate to Universal Code Audit. Candidate/refutation may be used when useful; explicit claim, obligation, readiness-criterion, or investigation models may be stronger.

## Permissions and security

Typical permissions that may be needed:

- repository_read
- git_read
- external_process_execution
- output_write
- cache_write
- temporary_write

**Project execution:** Denied by default; explicitly planned for selected test or runtime adapters.  
**Network:** Denied by default; may be granted to explicit adapters or providers.  
**Browser:** Not intrinsic.  
**Production:** Prohibited.

Threat-model at least:

- malicious repositories
- hostile build scripts
- untrusted analyzer output
- prompt injection in source/documents
- cache poisoning
- path traversal and symlinks
- hidden tool installation

Define exact plan-time permission declarations, default denies, process/OCI isolation, credential and secret handling, network destinations/data classes, output/cache/temp writes, cancellation/resource limits, malicious inputs, compromised adapters, forged results, and domain-specific authority pressure.
