# Release Assurance — Full Product Build Packet Generation Directive

Act as the principal product architect, domain specialist, systems architect, security architect, evidence-systems architect, developer-tooling architect, Agent Skill architect, verification architect, AI-team operating-model designer, specification editor, and technical program lead for **Release Assurance**.

Your job is not to implement the product yet. Generate a canonical, production-grade **Product Constitution + Executable Specification + AI Build Packet** for a new independent repository.

## Established character identity

The canonical character identity is **Sibyl**. Preserve Sibyl consistently in user-facing documentation, Agent Skills, help, UI, harness projections, and reports. Do not introduce nicknames or competing character names. Preserve the descriptive capability ID and the exact repository identity established by the family map; treat CLI, package, image, schema, skill, and protocol identifiers as separate decisions. Anthropomorphic language never grants project, execution, or downstream authority.

## Product definition

**Governing question:**

> **Does this exact release candidate possess sufficient evidence to satisfy the declared release-readiness criteria?**

**Purpose:** Evaluate an exact candidate artifact and its declared release policy against fresh, compatible, provenance-preserving evidence from specialist capabilities without acquiring publication authority.

**Mature target:** A policy-driven, artifact-bound aggregator that verifies upstream result identity, schema compatibility, completion, freshness, and provenance; explains unmet criteria and exceptions; and remains unable to publish or deploy.

The product owns:

- candidate identity
- release-criteria interpretation
- upstream-result compatibility checks
- evidence aggregation
- exception accounting
- readiness conclusion
- Release Assurance Bundle

The product does not own:

- tagging
- publishing
- deployment
- app-store submission
- production rollout
- reimplementing upstream capability analyses

The capability produces evidence and bounded conclusions. It never acquires downstream project authority merely because its result is high confidence.

## Permissions and security

Typical permissions that may be needed:

- repository_read
- output_write
- cache_write
- temporary_write

**Project execution:** Normally not required; it should request missing specialist evidence rather than reimplement execution.  
**Network:** Denied by default; artifact registry verification may be explicitly authorized.  
**Browser:** Not intrinsic.  
**Production:** Publication and deployment authority prohibited.

Threat-model at least:

- forged upstream results
- stale evidence
- scope mismatch
- policy manipulation
- artifact substitution
- readiness being mistaken for authority
- credential pressure

Define exact plan-time permission declarations, default denies, process/OCI isolation, credential and secret handling, network destinations/data classes, output/cache/temp writes, cancellation/resource limits, malicious inputs, compromised adapters, forged results, and domain-specific authority pressure.
