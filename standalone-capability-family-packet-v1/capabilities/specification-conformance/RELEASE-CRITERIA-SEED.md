# Specification Conformance Mature-v1 Release Criteria Seed

A project-generation agent must turn these into a precise claim-proof matrix.

- independent CLI operation without Octon Mini, MCP, or AI
- one authoritative engine across released interfaces
- valid, documented, verifiable Conformance Bundle
- truthful completion for missing/denied/failed/stale/partial evidence
- explicit permission planning and no hidden installation/network
- domain-specific golden, near-miss, adversarial, security, and large-subject evaluation
- stable result identity, comparison, provenance, and corruption detection
- signed/checksummed release artifacts with SBOM/provenance as applicable
- canonical Agent Skill with routing and authority tests
- canonical character identity **Ortha** propagated without aliases or authority expansion
- documented limitations and capability depth rather than a misleading supported yes/no claim

## Domain-specific release outcomes

- conclusion states are precisely defined: satisfied, partially_satisfied, violated, unimplemented, unverified, ambiguous, superseded, not_applicable;
- evaluation establishes: ground-truth traceability, ambiguity detection, false conformance rejection, authority-conflict preservation, coverage of declared requirements, stable mapping across refactors;
- domain threats have passing controls: malicious or stale specifications, prompt injection in documents, authority spoofing, ambiguous identifiers, outdated architecture diagrams, silent supersession;
- selected adapters/providers have version matrices, contract tests, and named owners;
- mature target is satisfied: A source-authority-aware traceability and conformance engine that maps requirements and decisions to code and proof, supports architecture fitness checks, preserves conflicts and ambiguity, and produces revision-stable conformance status.

A high feature count does not substitute for coherent evidence, completion, security, and interface semantics.
