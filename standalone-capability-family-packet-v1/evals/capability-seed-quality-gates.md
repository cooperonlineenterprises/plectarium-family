# Capability Seed Quality Gates

Every seed must pass these gates before its project-generation prompt is used as canonical input.

## Product boundary

- canonical character identity matches the family mapping and remains distinct from technical identifiers and authority;
- governing question is precise;
- owned and prohibited responsibilities are explicit;
- authority limits are concrete and domain specific;
- mature-v1 ambition is production shaped.

## Architecture

- authoritative engine and interfaces are separated;
- durable result type is named;
- external-tool strategy prefers integration where appropriate;
- shared conventions are inherited with correct status;
- domain-specific semantics are not flattened into UCA concepts.

## Security

- typical permissions and denied defaults are explicit;
- domain-specific threat extensions are substantive;
- production mutation prohibitions are unmistakable where applicable;
- project execution/network/credential behavior is inspectable.

## Evidence and completion

- primary evidence sources are named;
- conclusion/status model is bounded and avoids exaggerated proof;
- partial/unavailable/stale behavior is addressed;
- imported evidence preserves provenance.

## Interfaces and skills

- descriptive-name and canonical-character triggers are covered without aliases or authority-expanding language;
- CLI/CI/MCP/OCI/harness/skill roles are defined;
- skill does not implement the engine;
- no interface silently escalates authority;
- project prompt calls for cross-interface equivalence.

## Evaluation and roadmap

- claims have proof categories and adversarial/near-miss cases;
- release criteria match mature target;
- roadmap begins with contracts and Minimum Complete Architecture, then full depth;
- research agenda includes primary tools, standards, and domain failure modes;
- open questions state whether work can proceed.
