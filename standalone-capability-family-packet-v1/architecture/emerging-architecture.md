# Emerging Architecture and Stabilization Policy

The family architecture is deliberately split into three authority levels.

## Established

- independently usable capabilities;
- harness-agnostic cores;
- one semantic engine per capability;
- evidence-not-authority;
- explicit permission review;
- no hidden installation/network;
- truthful completion;
- thin skills/interfaces;
- cross-capability provenance preservation;
- no universal framework yet.

## Accepted reference patterns

- discover → plan → permission review → execute/analyze → evidence → completion → durable result → inspect/compare;
- canonical CLI plus CI/MCP/OCI/skill/harness projections;
- out-of-process/OCI specialist adapters;
- production-shaped build in dependency order.

## Provisional experiments

- `standalone-capability-manifest.v0`;
- `standalone-capability.result-envelope.v0`;
- common completion schema v0;
- permission vocabulary v0;
- capability classes;
- common result-reference/import records;
- exact discovery and harness-provider transport.

## Deferred extraction

Shared SDKs, hosted registries, plugin runtimes, installer frameworks, generic policy languages, common queues, and marketplaces remain deferred. Extraction requires demonstrated duplication across real implementations and must reduce total complexity rather than merely relocate it.
